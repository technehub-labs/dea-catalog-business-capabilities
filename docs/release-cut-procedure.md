# Release-Cut Procedure (dea-catalog-business-capabilities)

**Status**: Active (CR-DEA-BC-36, 2026-10-13)
**Owner**: Coder (for eaojnr)
**Depends on**: `docs/VERSIONING.md` (version-trigger table; prior-cut history table); the 7 catalog validators in `scripts/`

The release-cut procedure governs the gate from "main is green" to "a new release tag is pushed to origin and a GitHub Release is created (optional)". Every step is mandatory; no shortcuts; the pre-release CI verification contract (A) and the GPG-signing procedure (D) are the two extensions from the CR-BP-116 candidate list that were adopted by CR-DEA-BC-36 (sequence A to F).

## 1. Decide the target version

Read the version-trigger table in `docs/VERSIONING.md` and decide the next version. Document the rationale (which entries changed; which PR is the carrier; the bump tier: major / minor / patch) in a new `change-requests/CR-DEA-BC-NNN.md` file (the carrier CR). The carrier CR is the audit trail for the cut; the release manifest references it.

## 2. Add the release-notes file

The carrier PR adds a `release-notes/vN.M.P.md` file with:

- Trigger CR reference (the carrier CR's id).
- The 7-gate posture: blocking CONFORMANT count + advisory CONFORMANT count + the full list of any advisories (or `none`).
- The proposed tag SHA (this is the SHA that will be tagged, captured as `git rev-parse origin/main` at the moment of tagging in step 4; the carrier PR's merge SHA is the same value).
- A one-paragraph user-facing summary of the release (what changed; who is affected; what to migrate).

The release-notes file is committed in the carrier PR; it is the body of the eventual `gh release create` (or, if no GitHub Release, the in-repo changelog anchor).

## 3. Merge the carrier PR (no direct-push)

The carrier PR is opened against `main`. PR review is mandatory. The carrier PR is merged only after step 8 verification (the 7-gate rollup).

## 4. Pre-release CI verification contract (A)

The proposed tag SHA is `git rev-parse origin/main` captured at the moment of tagging. A fresh CI run on that exact SHA (the carrier PR's push) must complete with all 3 workflows SUCCESS:

- `validate` (the general 7-gate rollup)
- `ecf-conformance-consumer` (the ECF conformance consumer-side check; ensures the catalog still conforms to `dea:ecf@1.0.0`)
- `id-system-coherence` (the org-wide id system coherence check; ensures IDM-001..007 are CONFORMANT and IDM-008 PR-scoped coherence passes)

If any workflow is red, fix it before tagging. Do not tag a red-SHA release. The race this catches is the v1-alpha.0 / v0.1.0 / v0.3.0 class where web edits land after the carrier PR merges and the tag ends up pointing at a SHA the catalog was regenerated against a different version of.

## 5. Run the 7-gate rollup locally

The carrier-PR-merged state must pass the 7-gate rollup on the local checkout:

```bash
python3 scripts/check_naming.py                   # exit 0
python3 scripts/check_versions.py                 # exit 0
python3 scripts/check_ecf_conformance.py          # exit 0
python3 scripts/check_view_refs.py                # exit 0
python3 scripts/check_visual_domain_labels.py     # exit 0
python3 scripts/check_catalog_index.py            # exit 0
python3 scripts/check_id_system.py                # exit 0 (IDM-001..007 CONFORMANT)
```

If any script exits non-zero, fix it before tagging. Do not tag a red-SHA release.

## 6. CATALOG.yaml regeneration

The 7-gate rollup includes the catalog index check; the catalog index is regenerated by the `check_catalog_index.py` script. The release-cut step confirms that the regenerated CATALOG.yaml is the one on `main` and that the `open_change_requests` count, the entity `last_modified` timestamps, and the catalog `catalog_version` field are all consistent with the carrier CR.

## 7. GPG-signing procedure (D)

The active key fingerprint is `B2FD3524B35CBDD34251ABE07969C942DB14B2F2` (per `~/.hermes/profiles/coder/secure-notes/gpg-signing-setup.md`). Verify the key is available:

```bash
gpg --list-secret-keys --keyid-format LONG | grep B2FD3524B35CBDD34251ABE07969C942DB14B2F2
```

If the key is missing, the secure-notes procedure (`~/.hermes/profiles/coder/secure-notes/gpg-signing-setup.md`) walks through restoring the key. Do not cut a release without the key.

Cut the tag:

```bash
git tag -s vN.M.P -m "<commit-message-template>" <carrier-merge-sha>
```

The `<commit-message-template>` is the standardised message: `dea-catalog-business-capabilities vN.M.P: <one-line summary>; carrier CR-DEA-BC-NNN; <gate-count> gates CONFORMANT`. The template is the CR-DEA-BC-116 deferred G item; this CR uses the de-facto template until a future CR formalises it.

Verify the signature immediately:

```bash
git tag -v vN.M.P
```

The `git tag -v` output must show `Good signature from ...` with the key fingerprint `B2FD3524B35CBDD34251ABE07969C942DB14B2F2`. The verification status (PASS/FAIL + the key fingerprint) is added to the release manifest in step 10.

## 8. Push the tag

```bash
git push --tags
```

`git push --tags` pushes all local tags. For a single-tag push, use `git push origin vN.M.P`. The tag is now on `origin`.

## 9. Optional: GitHub Release

```bash
gh release create vN.M.P \
  --repo technehub-labs/dea-catalog-business-capabilities \
  --title "vN.M.P" \
  --notes-file release-notes/vN.M.P.md
```

The GitHub Release is optional: the first real cut may decide to defer it. If deferred, the carrier CR records the rationale and the release is announced via the in-repo changelog + the `dea-catalog-release-cut` skill (cross-repo coordination note).

## 10. Update the prior-cut history table

In `docs/VERSIONING.md`, immediately below the version-trigger table, append a new row to the prior-cut history table:

```
| version | date | cut by CR | commit SHA | gates (blocking+advisory CONFORMANT) | post-mortem |
| ------- | ---- | --------- | ---------- | ------------------------------------ | ----------- |
| vN.M.P  | YYYY-MM-DD | CR-DEA-BC-NNN | <tag SHA> | 7+0 CONFORMANT | (post-mortem link, if any) |
```

The post-mortem column is optional; link a retrospective if one exists.

## 11. Cross-repo coordination

Any release that lands a `capabilities:*` id set change or moves the ECF version triggers a sweep of sibling repos for downstream breaks before the next cut cycle:

- `technehub-labs/dea-metaframework`
- `technehub-labs/dea-architecture-framework`
- `technehub-labs/dea-catalog-processes`
- `technehub-labs/dea-catalog-business-objects`
- `technehub-labs/dea-catalog-organizational-units`
- `technehub-labs/dea-catalog-actors`
- `technehub-labs/dea-catalog-business-services`
- `technehub-labs/dea-catalog-stakeholders`

The sweep is `gh search code "dea-catalog-business-capabilities@vN.M.P" --owner technehub-labs` (or the local-repo grep equivalent if the API is unreachable). The next cut cycle begins with a record of the sweep in the carrier CR.

## 12. Recovery

If a cut is later found to be pre-mature (the v0.x / v1-alpha.x class of incident), the recovery procedure is:

1. Capture a recovery appendix in the corresponding CR (the model is `change-requests/CR-DEA-BC-NNN-release-history-reset-and-discipline.md`).
2. Cross-repo dependency sweep (§11) before any destructive operation.
3. Delete the local tag (`git tag -d vN.M.P`).
4. Push the deletion (`git push origin :refs/tags/vN.M.P`).
5. Delete the GitHub Release if one was created.
6. CHANGELOG.md: move the `[vN.M.P]` section into `docs/release-history-archive.md` and consolidate `[Unreleased]` to the top.
7. CITATION.cff: bump `version` to the next intended cut (or back to `0.0.0` for a full reset); remove `date-released` if no release exists.
8. Carrier CR relabel: `[WITHDRAWN YYYY-MM-DD — see CR-DEA-BC-NNN]` on the title row in `change-requests/README.md`; Status header addendum on the carrier CR doc.
9. CATALOG.yaml regen: `open_change_requests` count +1; all other counts unchanged.
10. 7-gate rollup CONFORMANT; CI green on the merged PR.

The procedure in `change-requests/CR-DEA-BC-36-release-history-reset-and-discipline.md` is the worked example of steps 1-10 for the v1-alpha.x class of cuts; reference it for any future reset.
